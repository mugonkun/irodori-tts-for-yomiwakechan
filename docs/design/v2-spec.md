## 1. 言葉の対照表

### 1-1 規則（これを先に決める）

1. **画面・公式ページ・使い方ガイド・リリース文からは、内輪の語を 1 語も出さない。**
   内輪の語＝**変種・実行系・取得台帳／台帳・潜在／参照潜在・焼く／焼き印・裁定の番号・`decisions.md`・
   元実装の commit・wrapper・門／便**、および「サーバ配布」の枠組みを映す物＝
   **帯に流れるサーバの生ログ行・ポート番号（例外は 1 件・§2-1）・「上流」という言い方**。
2. **世間で通じる技術語は隠さない。** 所有者の指示（2026-09-10）＝「**bf16 や FP32 などの検索で助けになる
   語句はそのままでいい、CUDA や ROCm もその想定**」。**CUDA・ROCm・cu126／cu130・GPU・VRAM・NVIDIA・
   AMD・Radeon・GeForce・RTX・ドライバとその版の数字・bf16・FP32・Windows・wav・Python** は、
   **役に立つ場所には原語のまま出す。言い換えない・伏せない。**一覧は §1-2b。
3. **判定は憲章 原則 1 の検分文（2 段）で行う**＝⑴ その語を検索して**このリポと無関係な誰かの解説**が出るか
   ⑵ **その場所で利用者が下す判断（選ぶ・直す・待つ）に直結するか**。**2 つとも通った語だけを出す。**
   `サーバ`・`ポート`・`キャッシュ` は⑴を通るが⑵で落ちる。`bf16`・`cu126`・`ROCm`・`ドライバの版` は 2 段とも通る。
4. **識別子は 1 字も変えない。** `settings.json` の鍵（`variant`・`precision`・`port`・`autoStartServer`・
   `precomputeOnStart`・`acceptedNoticesSha256`…）、台帳の檔名（`ledger/runtime-rocm-gfx1151.json`）、
   `runtime\<variant>\` の路、契約（`/ywk/status` の `variant`・`device`・`precision`）、env（`YWK_VARIANT`）、
   C# の型（`ReleaseFlavor.Radeon`・`RuntimeVariants.Cu130`）、ログ檔の行、
   `AutomationProperties.AutomationId`、インストーラの `AppId`・導入先・資産の檔名＝**すべて現状のまま**。
   **足すことだけは許す**（新しい `AutomationId`・`/ywk/status` の新しい欄・利用者データ側の台帳の新しい欄）。
5. **保守用の文書（`docs/install.md`・`docs/contract.md`・`decisions.md`・設計書 `ben-*`）は替えない。**
   語彙が揃っていること自体が資産である。ただし「利用者に見せる札」を**原文のまま引いている註**は新しい札に直す。
6. **1 つの物に 1 つの名前。** 同じ物を「実行系」「変種」「ランタイム」と綴り分けない。
   利用者に見せるときは「**動かすための一式**」（物）と「**動かし方**」（選び方）の 2 語だけを使う。
7. **「詳細」の中は技術語のままでよい。** ただし見出しに必ず「**（上級者向け）**」を付け、
   冒頭に 1 行「ここは、うまく動かないときに中を見るための欄です。ふだんは見なくてかまいません。」を置く。
   **「詳細」は 1 画面・12 行以内**（憲章 原則 7）。**入らない物は、移さずに消す。**
8. **所有者が名指しで禁じた語が 1 つある**（2026-09-10）＝「原文をそのまま引く」意の漢語 2 字。
   利用者に届く文（公式ページ・`README`・リリース文・`docs/guide.md`）でも、この檔の分析の文でも、
   **「原文」「そのまま」と書く**。
9. **利用者に見える文字列は 1 箇所に集める。** `UiText` の隣に、画面に出る文字列だけを持つ表（`UserText`）を置き、
   **そこだけを別の目で読む**（憲章 §3 根 8）。ログへ落とす文はいままでの綴りのまま＝**画面用と記録用を分ける**。

### 1-2b 残す語（世間の技術語）― **隠さない・言い換えない**

所有者の指示（2026-09-10）による。**下の語は、判断の役に立つ場所には原語のまま出す。**

> `cu130 / cu126 / cpu / rocm-gfx1151` と `CUDA / ROCm` を**隠す側**に置いていた。

### 1-3 数の書き方

`UiText.Bytes` の 1024 進（`GiB`）は**是正済みの決め事**である（同じ値が配布物の中で `GiB` と `GB` の
2 通りに綴られていた欠陥を、名前を事実に合わせて直した）。表示用の別入口を足すと**その欠陥に戻る**。

**規則**＝
- **計算した実数を出す欄は `UiText.Bytes` のまま**（`GiB`）＝ただし置き場は**「詳細」の中**に限る。
- **利用者に見せる面では実数を出さない。**「**約 5.3 GB**」「**約 8 GB**」「**空き容量 12 GB ほど**」という
  **丸めた散文**を定数で持つ（書式関数を通さない）。単位の綴りが 2 つに割れないのは、
  片方が**測った値**、片方が**説明文**で、同じ数を指していないからである。
- **数は憲章 §4 の「数字の 1 枚表」だけを引く**＝ダウンロード **約 5.3 GB**／残る量 **約 8 GB**／
  作業に要る空き **約 12 GB**。**この 3 つ以外の数を利用者向けの面に書かない。**
- ウィザードの進捗も同じ＝既定は「**42 %　あと 6 分ほど**」（§3 段 3）。実数の内訳は詳細の中で `GiB` のまま出す。
- **更新の差分**（§11）だけは 4 つ目の数を出してよい＝「**約 320 MB**をダウンロードします（2 分ほど）」。
  これは**その回に実際に落ちる量**であり、丸めた散文ではなく台帳から数えた値を `GB`／`MB` に丸めて出す。

### 1-4 付録 ―「変種」は適切な語か → **適切ではない**

- 日本語の「変種」は生物・写本の**異本**を指す語で、ソフトの構成を指す用例が一般に無い。
  英語 *variant* の直訳だが、利用者がこの語から構成を連想する道筋が無い。
- そもそも**この語が指す物を利用者が知る必要が無い**。言い換えるのではなく**概念ごと画面から消す**のが正しい。
- どうしても人に見せる場面（設定の詳細）では「**動かし方**」と呼び、
  **値の側は世間の語**（`CUDA 13.0`・`CUDA 12.6`・`ROCm`・`CPU`）で出す＝ここは隠さない（§1-2b）。
- 内部の識別子（`variant`・`RuntimeVariants`・`YWK_VARIANT`・台帳名）は**そのまま**＝
  開発者に対しては *variant* が正確な語であり、直す理由が無い。

## 6. 名前 ―「RTX（CUDA）」「Radeon（ROCm）」にする

### 6-1 結論

**利用者に見えるすべての面で「RTX（CUDA）」「Radeon（ROCm）」に統一する。**
所有者の指示（2026-09-10）＝「**RTX(CUDA)、Radeon(ROCm)と併記で。**」（`decisions.md` 128-4）

**併記が正である。**次のどれも**使わない**＝「NVIDIA 版」だけ／「CUDA 版」だけ／「ROCm 版」だけ／
「Radeon 版」だけ。**利用者が自分で確かめられる語（RTX・Radeon）と、検索の助けになる語（CUDA・ROCm）を、
1 つの札に両方載せる。**

### 6-2 理由

1. **利用者が自分で確かめられる語が要る。** デバイスマネージャに出るのは `NVIDIA GeForce RTX 4070` と
   `AMD Radeon…` であり、`CUDA` も `ROCm` もどこにも書いていない。「CUDA 版」だけの札は
   **自分に当てはまるか判定できない**＝2 択が成立しない。**RTX／Radeon がその判定を成立させる。**
2. **同時に、技術語も要る。** `CUDA`／`ROCm` は世間で通じ、検索の助けになる語である。
   隠すと、調べようとした人の手がかりが消える。**併記なら、両方の役目が 1 つの札で果たせる。**
3. **いまの釦は既に自白している。** `site/index.html` は「**CUDA 版を落とす（NVIDIA）**」＝
   正解を括弧に入れている。**主従を入れ替え、括弧の中身を RTX に直す**だけで迷いが消える。
4. **`decisions.md` 125 の文**が「RTX 系の人は CUDA、Radeon 系の人は Radeon 版」＝**利用者側の語は既に RTX／Radeon**。
5. **左右の形が揃う。**「RTX（CUDA）」「Radeon（ROCm）」は〈製品名（技術名）〉で同型である。
6. **嘘にならない。** Radeon（ROCm）の中では `cpu` も選べるが、**版の名は「どちらの機体向けか」を指す札**であり、
   その機体で既定として使う計算基盤の名を括弧に入れているだけである。
   CPU で動かしている人には、設定の詳細と詳しい状態の 1 行が「CPU で動かしています」と別に告げる。

```jsonc
// 足す欄（トップレベルの鍵 1 つ・中は 1 欄だけ）
"requests": { "in_flight": 0 }
```

  「いま読み分けちゃん2 の読み上げに使われています」（**自分の射を引く唯一確実な手**）。

## 11. 更新の差分取り直し（`decisions.md` 115 の穴・憲章 §4-24 の必須要件）

> **この §11 が更新の差分の正本である。**名前（`PresetSync.Plan`／`RuntimeDiff.Plan`／`ModelDiff.Plan`）・
> データ樹の写しの路（`runtime\<variant>\.ledger.json`）・台帳の新しい欄（`preset_md5`・1 行ごと）・試験の本数（約 20 本）は
> **この檔の綴りを使う**。`v2-plan.md` 段 E は**この名前・路・欄名を引き写す**（別の名を立てない）。
> 逆に、plan が持っていた 2 つの規律は**こちらへ取り込んだ**＝⑴ **版が変わった回だけ走らせる**（§11-2）
> ⑵ **`origin=preset` の行だけを相手にする**（§11-2）。**新設 id の一覧は `launcher/README.md` §7-3 の表に 1 本化する**（§2-0）。

### 11-0 いま何が起きているか（穴の実物）

憲章 §4-24 は「同梱の声や動かす部品が新しくなった版では、開いたときに**その差分だけ**を取り直す
（1 分程度・全部を落とし直すことはしない）」を **v2.0 の必須要件**と定めた。**いまは無い。**

`decisions.md` 115（2026-09-05 の実射）が見つけた穴を、コードの実物で言い直す＝

```csharp
// launcher/IrodoriTtsYwk.Launcher/Services/Voices/PresetVoices.cs
private static bool CopyReference(VoiceStore store, PresetVoice preset)
{
    var destination = Path.Combine(store.ReferencesDir, preset.FileName);
    if (!File.Exists(destination))                      // ← ここ
    {
        File.Copy(preset.SourcePath, destination, overwrite: false);
    }
    return true;
}
```

**檔が在れば 1 バイトも書かない。** だから配布側が wav を録り直した版（`decisions.md` 114 の `calm_20s` 差し替えのような回）でも、
利用者のデータ樹には**古い音のまま**残る。`InstallIfFirstRun` は印が立った台帳に 0 を返し、
`InstallNew` は「**id が増えた**」回しか見ず、`Restore` も `skipExisting: true` なので、**3 本とも同じ穴を通る**。
一式（runtime）とモデルの側は、そもそも**丸ごと組み直す**しか道が無い。

**この §11 が塞ぐのは 3 つ**＝⑴ 同梱の声 ⑵ 動かすための一式 ⑶ 声のデータ（モデル）。
**塞がないもの**＝アプリ本体（exe・XAML・`licenses/`・配布樹側の `voices/`）＝**インストーラが丸ごと置き換える**ので差分は要らない。
**1 バイトも触らないもの**＝利用者が追加した声・`settings.json`・`logs/`。

### 11-1 「差分」の定義（3 つとも同じ 3 語で書く）

| 対象 | 差分の**単位** | **新旧を突き合わせる材料** | **利用者が触った物を守る規則** |
|---|---|---|---|
| ⑴ 同梱の声 | **wav 1 檔**（＝プリセット 1 名） | 配布樹の `voices/presets.json` の `presets[].secondary.md5`（と `size_bytes`）と、利用者データ側に**新しく記録する** `preset_md5` | **利用者が差し替えた wav は上書きしない**（11-2 の c 枝） |
| ⑵ 動かすための一式 | **台帳の item 1 つ**（＝wheel 1 檔） | 配布樹の `ledger/runtime-<変種>.json` と、展開が通った回に**データ樹へ置く写し** `.ledger.json` | 一式は利用者が触る物ではない。**旧にだけ在る item は消さない**（11-3） |
| ⑶ 声のデータ | **モデルの檔 1 つ**（`<repo>:<path>`） | 配布樹の `ledger/models.json` の `repos[].files[].sha256` と `revision` | **古い revision の snapshot は自動で消さない**（11-4） |

**「利用者が変えたか」の検出は md5（ないし sha256）の一致だけで決める。**
更新時刻もサイズも使わない＝**写しは時刻を持ち越さないし、同じ長さの差し替えを見逃す**。
`size_bytes` は md5 を計る前の足切りにだけ使う（長さが違えば計らずに「違う」と決める）。

### 11-2 ⑴ 同梱の声（プリセットの wav）

**足す欄（利用者データ側の台帳 `voices.ywk.json`・1 行につき 1 つ）**

```jsonc
"preset_md5": "0d2e0175c9db9f68dbd57a1ae2939440"   // この行の wav を置いた時点の、配布側の md5
```

**既存の欄は 1 つも変えない**（`preset`・`origin`・`file`・`ref_latent`・`presets_installed`・`presets_installed_ids` は据え置き）。
欄が無い行（v1.x が書いた台帳）は「**判らない**」として扱う。

**判定＝純関数 `PresetSync.Plan(manifest, table, measuredMd5)`**（檔を触らない・単体試験で全枝を当てる）

| 枝 | 条件 | する事 | 利用者に見せる |
|---|---|---|---|
| **a** | 利用者データに wav が無い | **写す**（いまと同じ） | 何も出さない |
| **b** | 在る。実測 md5 ＝ `preset_md5`（前に置いた版）で、配布側の `secondary.md5` と違う | **上書きする**（利用者は置いたまま触っていない） | E3＝「最初から入っている声が新しくなりました（**n 名**）」＋〔取り込む〕 |
| **c** | 在る。実測 md5 ≠ `preset_md5` | **触らない**（利用者が差し替えた） | 取り込みのあと 1 行＝「**あなたが差し替えた声はそのままにしました（n 名）。**」 |
| **d** | 在る。実測 md5 ＝ 配布側の `secondary.md5` | 何もしない（もう新しい） | 何も出さない |
| **e** | 在る。`preset_md5` が無い（v1.x の台帳） | **触らない。**ただし実測 md5 ＝ 配布側の `secondary.md5` なら **`preset_md5` を書き足すだけ**（次の版から b が効く） | 何も出さない |

**守る規律（いまの物を 1 つも壊さない）**
- **消したプリセットは戻さない**＝`presets_installed_ids` に居て台帳に居ない id は、差分でも**触らない**（`decisions.md` 121 の規律）。
- **改名の引き継ぎ（`MigrateRenamed`・`decisions.md` 108）は先に走らせる**＝改名で新しい名になった行に対して差分を当てる（順序が逆だと同じ檔を 2 名が指す）。
- **wav を上書きした行は、下ごしらえ（`ref_latent`）を捨てる**＝`.pt` と sidecar を消す（`VoiceStore.DeleteLatentFiles`）。
  焼き直しは起動時の事前計算に任せる（`MigrateRenamed` と同じ手）。**捨てないと、新しい wav に古い音の下ごしらえが当たる。**
- **`origin=preset` の行だけを相手にする**＝利用者が足した声は別の id になる。
  `file` が `refs/` の外を指す行は飛ばす。**この 2 つを試験で釘付けにする**（利用者の声を消す事故は取り返しがつかない）。
- **版が変わった回だけ走らせる**＝`settings.InstalledAppVersionFor(variant)` が今の版と違う回だけ。
  **毎起動で 12 檔（35 MB 級）を読ませない。**2 度目からは台帳に記録した `preset_md5` と配布側の `secondary.md5` の
  **文字列比較だけ**で済み、実測は**その版の初回だけ**でよい。
- **実装に要る 2 つ**＝⑴ `PresetVoice`（`Services/Voices/PresetVoices.cs` の `record`）に **`string? SourceMd5`** を足し、
  `presets.json` を読む所で `secondary.md5`／`size_bytes` を拾う（いまの `record` は md5 の欄を持たない）。
  ⑵ **md5 を計る小さな純関数を 1 本**足す（`System.Security.Cryptography.MD5.HashData`）＝
  `launcher/` の C# には MD5 の実装も参照も 1 つも無い。`AnalysisLevel=latest` の樹で 0 警告を掲げているので、
  **`CA5351` を落とす註つきの `#pragma`** を添える（**用途は完全性の照合であって暗号ではない**）。
- **走る場所**＝起動時の `InstallNew` の**すぐ隣**（`LauncherComposition.PrepareVoices` の ⑸ の後）。
  順（改名 → 初回展開 → 増えた分 → 中身の更新）を崩さない。**ネットは要らない**（配布樹の中の wav を写すだけ）＝
  12 名ぶんの md5 を計っても**1 秒級**。§4-24 の「1 分程度」はモデル側（11-4）の話である。
- **既定は「取り込む」を自動でやる**（`SettingsDifferentialUpdateCheck` が ON）。OFF の機体では E3 の 1 手を出すだけで、押すまで写さない。

**なぜ `presets.json` の md5 を信じてよいか**＝この欄は **`make_presets.py` が `--copy` の複写後に実檔から測った値**であり
（`voices/presets.json` の `notes` にそう書いてある）、`N:` の写しとの突合にも同じ md5 を使っている＝**既に台帳の一部として運用されている値**である。
新しく測り直す仕掛けは要らない。

### 11-3 ⑵ 動かすための一式（runtime の台帳）

**いま在る道**＝`RuntimeStamp.Compare` が `settings.runtimeLedgerSha256` と配布樹の `ledger/runtime-<変種>.json` の sha256 を
突き合わせ、違えば「実行系を組み直す」1 手を出す（`decisions.md` 91）。**判定は既に在る。**
**穴は「その 1 手が丸ごとしか無い」こと**＝4 GB 級の再展開で、しかも `decisions.md` 90 で取得キャッシュは空なので
**実際は数 GiB の再ダウンロード**になる。

**足す物＝展開に使った台帳そのものの写し 1 檔**

```
<データ樹>\runtime\<variant>\.ledger.json    ← データ樹の中（配布樹には 1 檔も書かない）

  RTX（CUDA）  ＝ %LOCALAPPDATA%\irodori-tts-ywk-cuda\runtime\<variant>\.ledger.json
  Radeon（ROCm）＝ %LOCALAPPDATA%\irodori-tts-ywk-radeon\runtime\<variant>\.ledger.json
```

**データ樹は版ごとである**（`decisions.md` 133＝§11-8）。路は `AppPaths` から取り、**綴りを直書きしない**。
2 つの版が同じ機体に入っていても、`.ledger.json` は互いに見えない＝**差分の判定も版ごとに独立する**。

展開が通った直後、`RuntimeStamp.Burn` と**同じ回**で置く（片方だけ残さない）。

**判定＝純関数 `RuntimeDiff.Plan(oldLedger, newLedger)`**

| 枝 | 条件 | する事 |
|---|---|---|
| 1 | 同じ名で `sha256` が同じ | **触らない** |
| 2 | 同じ名で `sha256` が違う | **その 1 檔だけ**落として入れ直す |
| 3 | 新にだけ在る | 落として入れる |
| 4 | 旧にだけ在る | **消さない**（site-packages から wheel 1 つを安全に抜く手が無い）。ログに 1 行残す |

**歯止め 4 つ**
- **差分の回は `WheelInstaller` を `CleanBeforeInstall = false`・`RemovePartialOnFailure = false` で構える。**
  既定はどちらも `true`（`Services/Ledger/WheelInstaller.cs`＝組み直しの頭で変種ディレクトリを丸ごと `Directory.Delete` し、
  失敗すると丸ごと消す）＝そのまま差分を流すと ⑴ 頭で既存の一式が消えて「差分だけ落とす」意味が無くなり、
  ⑵ 差分の 1 檔が落ちただけで動いていた一式が丸ごと失われる（全部落とし直すより悪い）。
- **ゆえに差分が途中で落ちた機体は「新旧が混ざった樹」で残る。**締めに `RuntimeStamp.LooksComplete` と
  `WheelInstaller.ExpectedDistInfoCount` を**必ず撃ち**、合わなければ**その場で丸ごと組み直しへ落とす**
  （`decisions.md` 91 の規律をそのまま使う）。**`.ledger.json` は全部終わってから置く**（途中で落ちた回は次回また全差分）。
- **落ちる量が台帳全体の 6 割を超えるなら、差分をやめて丸ごと組み直す**＝半端に混ざった樹を作らない。
- **`.ledger.json` が無い機体**（v1.x から上がってきた樹）は差分を組めない → **その 1 回だけ丸ごと**。次の版から差分が効く。

**画面**＝帯の 1 手を「**〔動かすための一式を新しくする〕**」に替える（`StatusRebuildRuntimeButton`・id 据え置き）。
**押す前に量を告げる**＝「**約 320 MB をダウンロードします（2 分ほど）。**」進捗は既存の
`StatusRebuildProgressBar`／`StatusRebuildProgressText`／`StatusRebuildCancelButton` をそのまま使う（id 据え置き）。
**丸ごとに落ちる回だけ**「約 5.3 GB をダウンロードします（10 分ほど）」と告げる＝**嘘の見積りを出さない。**

### 11-4 ⑶ 声のデータ（モデル）

**いま在る道**＝`ledger/models.json` は **repo ＋ revision（commit）＋ files（path・sha256・size）**で pin してある
（現行＝3 repo・22 檔）。`AcquisitionCheck` は「その revision の檔が `HF_HOME/hub` の
`models--<org>--<name>/snapshots/<revision>/<path>` に在るか」だけを見る。

**穴だと思っていた物は、穴ではない。**`server/ywk_fetch_models.py` は `hf_hub_download(cache_dir=hub_cache)` を使う。
huggingface_hub の cache は **`blobs/<etag>` で中身を共有する**ので、revision が動いても**中身が同じ檔は
新しい `snapshots/<revision>/` に張り直されるだけでネットには出ない**。
つまり **差分は既存の取得の道が既に持っている。新しい取得系も新しい純関数も要らない。**

**要件は 3 つだけ**

1. **更新のときに `HF_HOME`（利用者データ樹）を消さない。**（消すと blob の共有が失われ、丸ごと落ち直す。）
2. **`refs/main` を新しい revision で書き直す**（`decisions.md` 49＝これが無いと offline で読み込みが落ちる。
   `ywk_fetch_models.py` が既にやる）。
3. **落ちる量の見積りは `ledger/models.json` の `sha256` が変わった檔の `size` の和で出す**
   （押す前に量を告げるため＝§11-3 と同じ規律）。

- **`ModelDiff.Plan` は「見積り専用の純関数」に格下げする**＝何 MB 落ちるかを数えるだけで、**檔を動かさない**。
  旧案の「古い snapshot から新しい snapshot へ hard link を張る」は**既に済んでいる仕事の作り直し**であり、
  しかも hub cache の作法（Windows で symlink が張れないときはコピーへ落ちる）を手で壊す危険がある。**採らない。**
- **見積りに使える `sha256` は LFS の 10 檔だけ**（＝落ちるバイトのほぼ全部）。
  残る 12 檔（`.gitattributes`・`README.md` など非 LFS）は `sha256` が `null` で、契約の註のとおり
  **git blob sha1** で検証する＝見積りでは `size` を足すだけにするか、**毎回 `hf_hub_download` に任せる**（小さいので実害が無い）。
- **古い revision の snapshot は自動で消さない**＝前の版へ戻れなくなる。
  設定 › 詳細ではなく**〔動かすための一式を新しくする〕の隣**に〔**古い声のデータを消す**〕を置き、
  **消せる量を先に出す**（「約 3.3 GB を消せます」）＝設定の詳細は 10 行で埋まっている（§2-5）。
- **見当**＝上流が触るのはたいてい 1 repo の 1〜2 檔なので、落ちるのは数十〜数百 MB。**憲章 §4-24 の「1 分程度」はここが根拠**である。

### 11-5 走らせる場所と、利用者から見た姿

```
アプリを開く
  └ 起動の前の安い検査（窓が開く前・通信なし・python を起こさない）
      ├ AcquisitionCheck（いまのまま）
      ├ RuntimeStamp.Compare  → 違えば E1「動かすための一式が、いまのアプリと合っていません」＋量つきの 1 手
      ├ ModelDiff.Plan（台帳どうしの突合だけ・檔は数えない） → 要るなら E1 と同じ帯に畳んで 1 手
      └ PresetSync.Plan（12 名の md5・1 秒級） → b が 1 件でも在れば E3「最初から入っている声が新しくなりました」
```

- **どれも「使えます」を妨げない**＝差分が要るだけの回は、**アプリはふつうに動く**。帯は緑のまま、1 手だけが増える。
  （動かない回＝`RuntimeStamp` が `LedgerChanged` を出す回は、いまのとおり赤の 1 手になる。）
- **`SettingsDifferentialUpdateCheck`（既定 ON）**が ON なら、**声の差分だけは黙って取り込む**（1 秒級・ネット不要）。
  一式とモデルの差分は**必ず押させる**（ダウンロードが走るから）。
- **憲章 §4-24 の文はそのまま真になる**＝「同梱の声や動かす部品が新しくなった版では、開いたときに**その差分だけ**を
  取り直す（1 分程度・全部を落とし直すことはしない）」。

### 11-6 試験と実射

**単体（純関数だけで書ける＝檔を触らない）**
- `PresetSync.Plan` の 5 枝 × 境目（md5 が空・台帳に欄が無い・消された id・改名の直後）＝**約 10 本**
- `RuntimeDiff.Plan` の 4 枝＋6 割の歯止め＋`.ledger.json` 不在＝**約 7 本**
- `ModelDiff.Plan`（**見積り専用**）＝落ちる量の和・`sha256` が `null` の檔を飛ばすこと・空の台帳＝**約 3 本**
- 合わせて **xUnit を 20 本ほど足す**（現行 743＋1 skip → 763＋1 skip 前後）。

**契約**＝1 本も触らない（§11 は HTTP の口に一切関わらない）。

**実射（憲章 §7 段 5・上書き更新）**＝v(N) を入れた機体に v(N+1) を上書きし、次の 5 つを**数える**。
1. 自分で追加した声と `settings.json` が残っている。
2. 配布側が録り直したプリセットの wav が**新しい md5 になっている**（枝 b）。
3. 自分で差し替えたプリセットの wav が**そのまま残っている**（枝 c）。
4. 落ちたバイト数が、丸ごと取り直した場合より**小さい**（台帳から計算した見積りと実測が合う）。
5. 「使えます」までの時間が、差分の無い起動と**同じ程度**である（差分の判定が起動を遅らせていない）。

### 11-8 置き場は版ごと（`decisions.md` 133）― 差分の前に 1 度だけ走る移送

**RTX（CUDA）と Radeon（ROCm）は別のアプリである**（`decisions.md` 109 で分けた線を徹底＝133 ⑶）。
**データ樹も設定も声も共有しない。**§11 の差分は**この版の樹の中だけ**を見る。

| 何 | いま（v1.x） | v2.0 |
|---|---|---|
| データ樹の既定 | `%LOCALAPPDATA%\irodori-tts-ywk\`（**両版で共有**・`AppPaths.DataDirName` の定数 1 つ） | **版ごと**＝`…\irodori-tts-ywk-cuda\`／`…\irodori-tts-ywk-radeon\`（既定を `ReleaseFlavor` で分ける。`settings.json` の `dataDir`／env `YWK_LAUNCHER_DATA_DIR` の明示指定は**従来どおり優先**） |
| 単一起動の錠 | `Local\irodori-tts-ywk-launcher`（`App.xaml.cs:34`）と、窓を前に出す合図の口 `Local\irodori-tts-ywk-launcher-activate`（`:37`）＝**両方とも両版で 1 つ** | **どちらも版ごと**（別アプリなので互いを起こし直さない）。**錠だけ割って合図を残さない**＝合図は `AutoReset` の 1 本なので、共有のままだと一方の 2 個目の起動が**もう一方の窓**を前に出す。`.iss` の `AppMutex` も錠と同じ形に割る |
| 2 つ同時に開いたとき | — | **後から起きた側がつなぎ口の塞がりで止まる**＝帯は §2-1a の **C1／D1**（`18088` を出す唯一の面・憲章 原則 5 の例外。`v2-copy.md` §3-2 では **E-05**） |
| 旧い共有樹 | — | **初回の v2.0 起動で版の樹へ移す**（同じボリュームなら改名・両版が入っていた機体は写す）。移送は**差分の判定より前**に走る（順が逆だと「まっさらな樹」と読んで丸ごと落とし直す） |
| 削除 | 問いが 2 つ・既定は残す | **その版の樹を丸ごと消す。問わない**（`decisions.md` 132／133 ⑴） |

**削除の規則（`decisions.md` 133 ⑴⑵）**
- **消すのは、そのアプリが自分の置き場に持っている物すべて**＝ダウンロードした一式・モデル・
  取り込んだ声の写し（`voices\refs\`）・下ごしらえ（`.pt`）・`settings.json`・`logs\`・取得キャッシュ・MIOpen の db。
- **置き場の外には 1 檔も触れない。** 声を追加するときに利用者が選んだ元の wav は**利用者の檔**であり、そのまま残る。
- **問いは 1 つも出さない**（132 の「追加した声と設定を消しますか」も廃止）。無人（`/SUPPRESSMSGBOXES`）でも同じ。
- **もう一方の版の樹には触れない**（共有が無くなったので「道連れ」の場合分けごと消える＝旧 `ben-e` §5-4 の規則は廃止）。
- **旧い共有樹 `%LOCALAPPDATA%\irodori-tts-ywk\` も、もう一方の版が入っていないときだけ一緒に消す。**
  移送は**初回の v2.0 起動**でしか走らないので、⑴ v1.1.0 に上書き導入して**一度も開かずに**撤去した機体、
  ⑵ 下の ⑶（移送に失敗して旧樹を残した回）の機体では、消さないかぎり **約 8 GB が丸ごと居残る**＝
  裁定 132 が起こされた当の状態。もう一方の版が入っている回は**触らない**（向こうがまだ移送で要る）。
  判定は `.iss` に既にある `OtherFlavorKey` の `RegKeyExists`（`installer/irodori-tts-ywk.iss:418`）を使う。

**この §11 への効き**＝⑴ `.ledger.json`・`preset_md5`・`HF_HOME` はすべて**版の樹の中**にあり、
2 つの版は互いの差分を見ない（同じ機体で 2 度落とすことになるが、**別アプリだから正しい**）。
⑵ 移送を通った回の樹は「v1.x が置いた樹」なので、§11-3 の**`.ledger.json` 不在の枝**（その 1 回だけ丸ごと）と
§11-2 の**枝 e**（`preset_md5` の無い台帳）がそのまま効く＝**移送のために新しい枝を足さない**。
⑶ 移送に失敗した回は**移送しなかったことにして**（旧い樹を消さない）新しい樹で始める＝
利用者の声を失わない。旧い樹が残ったことはログに 1 行だけ残し、画面には出さない。

> **実装の落とし所は `v2-plan.md` 段 E-3**（`AppPaths` の既定・Mutex・移送・`.iss` の削除）。
> **路の綴りを増やさない**＝画面もログも `AppPaths` の値を通す（直書きの `irodori-tts-ywk` は 0 箇所にする）。
