## 1. 依頼（逐語）

> ・問題分析
> 読み上げに意味が通らない予測不能な語句が入る。原因はおそらく絵文字。
> irodori-ttsは特定の絵文字を感情として反映するが、対応していない絵文字は文字数にカウントして何を埋めたらいいかわからない状態になっている。
>
> ・対策
> irodori-ttsが対応している絵文字はそのまま渡す。
> 対応していない絵文字は削除して削除した分の文字数を詰める。
>
> 削除処理よりも辞書変換を優先する事。
> 削除した絵文字はログに出力。
>
> まずは対応している絵文字が開示されているはずなので情報を収集せよ。

### 3-1 `normalize_text`（`irodori_tts/text_normalization.py`）
- 固定置換＝タブ・`[n]`（と文字列 `\[n\]`）・全角空白を消す／`？！`→`?!`／`♥`→`♡`／`●◯〇`→`○`。
- 正規表現＝`[;▼♀♂《》≪≫①②③④⑤⑥]` を消す／ダッシュ類（U+2212・罫線 ─━ を含む）を消す／`～〜`→`ー`／`…{3,}`→`……`。
- 外側の括弧を剥く → **NFKC** → `...`／`..`→`…`。
- **45 種には触らない**（実測・NFKC でも不変）。FE0F（VS16）・U+200D（ZWJ）・肌色修飾子も消さない。
- **絵文字に触る所**＝`♥`（U+2665・Extended_Pictographic）→`♡`（非絵文字）・`♥️`→`♡`＋裸の FE0F・`♀♂` の削除・**NFKC が 22 の絵文字を字に戻す**＝‼→!! ⁉→!? ™→TM ℹ→i Ⓜ→M ㊗→祝 ㊙→秘 🈁→ココ 🈂→サ 🈚→無 🈯→指 🈲→禁 🈳→空 🈴→合 🈵→満 🈶→有 🈷→月 🈸→申 🈹→割 🈺→営 🉐→得 🉑→可（今は「祝」「満」等として読まれている）。wrapper は上流より前に本文を処理するので、素の Extended_Pictographic で削るとこれらの読みが消える → §6-2 の畳み表で前倒しする（Q7）。
- **wrapper で NFKC を本文全体に掛けてはいけない**＝上流は NFKC の前に固定置換を掛ける作りで、順序が変わると結果が変わる（`～🎉`→上流だけなら `ー`、全体 NFKC を先に掛けると `~`／`①🎉②`→`''` 対 `12`）。

### 3-2 トークナイザと text encoder（checkpoint の `config_json`）
- checkpoint が名乗る物＝`text_tokenizer_repo='sbintuitions/modernbert-ja-310m'`・`text_encoder_type='pretrained'`（ModernBertForMaskedLM・25 層・hidden 768・語彙 102,400）。`config.py:19` の既定 `sarashina2.2-0.5b` は**この checkpoint では使われない**。同梱 `tokenizer/tokenizer.json`＝Unigram・byte_fallback 有り・`<unk>`=0・語彙は modernbert-ja-310m の物と同一で、その元の `tokenizer.model` は sarashina2.2-0.5b／sarashina2-7b と同じ blob＝「sarashina 系の語彙」という呼び方は事実として正しい。
- `batch_encode`（`tokenizer.py:107-119`）は `truncation=True`・`max_length=255`＋BOS＝**本文は 255 token を超えた分が黙って捨てられる**（checkpoint の `max_text_len=256`）。byte fallback の絵文字は 1 個で 3〜5 token を食う。

### 3-3 継続時間（`duration.py:105-167`・`model.py:1317-1375`）
- `build_duration_features` は `char_count=len(text)`（512 字で頭打ち）・`token_count/256`・句読点数・`emoji_count`（56 種）などの 14 次元を作る。**v4.1-Small（`token_sum_dual_adarn_zero_no_aux`）はこれを読まない**。
- 実際の予測＝text encoder の各 token の状態から frame を予測（`softplus`＞0）し、**BOS を含む全 token で総和**（話者・caption の条件は AdaRN で入る）。字数・注釈数は入らない。
- 現場の実測（launcher-20261011.log）＝5 字で 1.44 s・7 字で 1.40 s・12 字で 2.12 s・4 字で 1.76 s＝字数に単調ではない。2026-09-15 には 1 字の本文が 77.5 frames（3.12 s）。
- 約 40 ms/frame（35.8 frames＝1.440 s）。予測 frames×0.04 は上流ログの `audio_seconds` と 1,962 件すべてで一致（§4-3）＝予測が音の長さをそのまま決める。

## 8. ログの行き先

- wrapper（uvicorn・上流 app・ywk_server・silentcipher）の **stderr 全行**がランチャに読まれ（`ServerProcess.OnLine:620-628` → `ServerStateMachine.ApplyLogLine:227-280`〔水準の篩なし・1000 字超は畳む〕→ `StatusViewModel.AppendLog:1031-1052`）、**檔** `<データ樹>\logs\launcher-<yyyyMMdd>.log`（`HH:mm:ss 本文`・UTF-8）には全行、「ログ」タブ（2000 行の環）には見張りの足音（200 の GET /ywk/status 等）を除いて落ちる。ランチャは `PYTHONUTF8=1`・`PYTHONIOENCODING=utf-8` を渡す（`ServerEnvironment.cs:172-175`）＝絵文字は残る。
- 実例（launcher-20261011.log）＝`03:17:44 INFO:irodori_openai_tts.app:speech synthesis started: model=irodori-tts voice=吉田くん format=wav chars=5` → `predicted duration frames=35.8 … (1.440s)` → `speech synthesis completed: elapsed=1.11s audio_seconds=1.44`。合成 1 回あたり既に約 17 行＝1 行足しても環の圧迫は無い。`chars=` は Python の `len`（符号点）。
- wrapper の `logger`（`logging.getLogger("ywk_server")`・書式 `%(levelname)s:%(name)s:%(message)s`）で 1 行出せば `speech synthesis started` の直前に並ぶ（無音の近道では started 行が出ない・先読みと本発話が交互に入り得る）。**本文そのものは書かない**。推奨の綴り＝種類ごとに集計（上限 10 種程度・1000 字の畳みに掛からない）・U+ 表記を添える（🏻 等は目に見えない）・**削る前後の符号点数と削った数**（§4-3 の測り直しに要る）・無音で返した印・寄せた旨（Q3）。

| L-3 | 続く `speech synthesis started … chars=M` | M が削除の行の「後」の字数と一致（どちらも符号点）。本体の「N字」は UTF-16 単位＝突き合わせには使わない |
| L-4 | 空になった射 | 削除の行に「無音を返した」旨。そのあとに `started` が**続かない**。access 行は `200` |
| L-5 | 対応 45 種だけの本文 | 削除の行が 0（素通し）。亜種のときは寄せた旨 |
| L-6 | 先読みの射 | 本体は読む前に合成する＝削除の行は「読まれたコメント」ではなく「POST」と 1 対 1（淘汰された射にも出る） |

### 13-2 本体側で増えてはならない物

| # | 見る物 | 合格 |
|---|---|---|
| B-1 | 配布版の檔で `POST /v1/audio/speech` の access 行が 4xx | **0**。基準値＝本機 31 檔・1,962 射がすべて 200。本体のアプリログはファイルに残らない（1000 行の環）＝ずっと見られる物差しはこの数 |
| B-2 | 本体のログ タブ／〔不具合報告〕の zip | 「本体側の不具合です（code=ywk_empty_input）」「内部でエラー（応答 400）（code=ywk_upstream_error）」が **0 行**。対の「見切り」も増えない |
| B-3 | PlaybackError「音声の形式が想定（PCM 16bit）と異なる」 | **0 行**。**音量が 1 未満のプロファイル**で絵文字だけの本文を読ませて確かめる（音量 1 だと検査が走らない） |
| B-4 | 本体の `latency-<日>.log` | 無音の射にも 1 行出る（配布版の行が途切れない） |
| B-5 | 名前キャッシュの命中 | 直す前の在庫が残る機体だけで（本機は在庫 0） |

### 13-3 現場の基準値との比較
- §4-3 の基準値（N≤3 で ≥2.0 s＝28.3%・BMP 外ありの N≤3＝76.9%・BMP 外なしの ρ≥1.5＝4.5%）を、直した後も同じ台本で採る。合格＝割合が下がる（目標値は司令官）。注意＝直した後の `chars=N` は削った後の字数・空になった射は `started` 行が出ないので母数から抜ける＝「削除の行があった射の数」と「無音を返した射の数」を並べて書く。話者ごと、または ρ で比べる。
- 削除の行を 1 週間ぶん集める（どの絵文字が多いか・空になった射が何回か）＝Q1（未開示 11 種）と Q5（© など）を見直す材料。

### 13-4 司令官の聴感（seed を固定し、直す前は v2.0.9 で同じ本文を撃って wav を残す）

| 本文 | 期待 |
|---|---|
| `こんにちは🎉今日もがんばろう` | 「こんにちは今日もがんばろう」と同じに聞こえる |
| `やったー🎉🎉🎉` | 「やったー」だけ |
| `🎉🎉🎉` | 無音のまま次へ進む（本体にエラー行が出ない） |

| `いいね❤️` | 「いいね」だけ |
| `ありがとう🙏🏻` | `ありがとう🙏` と同じ効き |

### 13-5 両機（Radeon／RTX）で行う
- 版は両機とも `/ywk/status.version` で確かめる（v2.0.9 からアプリ内更新が無人で入る）。RTX 席には N: で依頼し、先に名前キャッシュの在庫（`%LOCALAPPDATA%\yomiwakechan2\irodori-ywk\名前キャッシュ\`）を確かめてもらう。
- 判定は Python（`regex`）だけ＝GPU の別には依らないはず（推測）。Radeon の注意＝削ると出力長の分布が変わり、初めて見る長さで MIOpen の探索が走り得る（透かしで 1〜2 s）＝直した直後の遅れを直しのせいと取り違えない。
