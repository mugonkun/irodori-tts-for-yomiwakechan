# 25 — RTX 3090 機の第 2 回収（cu130・ONNX の CUDA EP／DirectML EP・手術版グラフ）

> 席＝Fable（主席）が回収して整理。実行＝司令官が 3090 機で `run-cuda-kit.ps1 -Variant cu130` を N:\ 上で走らせた（138.5 分）。cu130 の走行は修正版 `bench_onnx.py`（`onnxruntime.preload_dlls()` を呼ぶ・EP 失敗の逐語を記録）と、N:\ に追加した DirectML 手術版グラフ（`*_az0`・`*_dml`）を使っている。
> 回収物＝`lab/out/3090-results-cu130-1604/`（cu126 の `bench_cu126_*.json` も同居）。数値は `summary.md` から転記。

## 要点（10 行以内）

1. **cu130 も pin のまま導入**＝`torch 2.10.0+cu130`（cuDNN 9.12.0）・venv **3,193 MB**・`torch/` 2,649 MB（本機の cu130 自己検証 `21` §4 と同値）。ドライバ 591.86 で `cuda.is_available()=True`。**cu126・cu130 とも 3090 で動作＝上流の pin はどちらでも通る**。
2. **合成（bf16・常駐ウォーム）**＝長文 40 steps 1.192 s／RTF 0.109、10 steps 短文 0.503／長文 0.576（cu126 と同等）。**短文 40 steps だけ 1.496 s／RTF 0.398 と cu126（0.722）の 2 倍遅く、cold 1.281 s < warm 1.496 s の逆転**＝測定ノイズ（NAS 上の走行・他プロセス）か cu130 の bf16 GEMM 経路の差かは**未確認**（ローカル SSD での再走が要る）。fp32 は cu126 と同等（短文 0.872／長文 1.645）。
3. **`d_torch_guard` の 311〜563 秒は torch の入れ直しではない**＝`install.json` の `torch_repaired` は両 variant とも null。実体は **NAS 上の venv から `import torch`（DLL 2.5〜3.9 GB）を読む時間**。主席が cu126 回収時に「入れ直しの 9 分」と説明したのは誤り（ps1 の constraint 修正は無害だが効いていない）。**N:\ 直走行が全段の遅さの原因**。
4. **ONNX の CUDA EP が取れた**（ORT 1.29.0・CUDA 13・`preload_dlls()` 修正の効果）：`dit_step` fp32 **30.6 ms**（B=3）／`encode_conditions` 35.6 ms／`dacvae_decoder` fp32 38.1 ms（fp16 22.5 ms）／`silentcipher_watermark` 47.3 ms（**DFT 込みで動く＝ORT 1.29 なら透かしグラフも GPU に載る**）／`duration` 7.7 ms／`speaker_encoder` 8.0 ms。
5. **CUDA EP の fp32 差は 1e-2 級**（`dit_step` 9.4e-3・`encode_conditions` 3.1e-3）＝Ampere の TF32 既定（DirectML は 2.5e-5）。照合基準にするなら `use_tf32=0`。
6. **fp16 の DiT は CUDA EP でも壊れる**（`dit_step_fp16` の CPU EP 差 6.20＝DirectML の 6.20 と同値）＝**fp16 の破綻は DirectML 固有ではなく GPU EP 全般の問題**（グラフ側の op が原因の公算。原因 op は未特定）。デコーダの fp16 は両 EP とも正常（差 2e-3〜7e-3）。
7. **DirectML（3090）**＝`dit_step` 45.1 ms（8060S の 1.8 倍速）・手術版 `encode_conditions_sdpa_az0` **445 ms**（8060S の 209 ms より遅い・CUDA EP の 12 倍）・`dacvae_decoder_fp32_dml` 85.3 ms・`speaker_encoder_az0` 5.4 ms・透かしは 1.24.4 でロード不可（AMD と同じ）。無手術グラフは AMD と同じ箇所で落ちる＝**`23` の後処理 3 種はベンダ非依存で必要**。
8. **⒝の NVIDIA 見立て（短文 40 steps・端から端まで・未実測の段合計）**＝CUDA EP fp32：DiT ≈20×30.6＋20×約 15 ms ≈0.9 s＋条件符号化 36＋復号 38＋透かし 47＋duration 8 ≈ **1.05 s／RTF ≈0.28**。DirectML fp32：DiT ≈1.4 s＋条件符号化 445＋復号 85＋透かし（CPU 331）≈ **2.3 s／RTF ≈0.6**。
9. `torch.compile` は cu130 でも `TritonMissing`。VRAM ピークは cu126 と同値（bf16 3,079 MiB・fp32 4,134／4,682 MiB）。
10. **未確認**＝cu130 bf16 短文 40 steps の異常（再走）・⒝の NVIDIA 端から端までの実測・fp16 破綻の原因 op・cu130 の cuDNN 9.12 と cu126 の 9.10 の差の影響。

## 主席への注意

- ⒜の版選び＝**cu130 は配布 689 MiB 軽く・導入後 1.3 GB 軽く・3090（591.86）で動作**。ただし bf16 短文 40 steps の異常値が 1 回出ている＝既定にするなら A1 の敵対検分でローカル SSD 上の再走を条件に。cu126 は古いドライバ層（560.76〜579）向けの手動手順として残せる。
- ⒝＝NVIDIA でも DirectML の端から端までは ≈0.6（見立て）＝判断則 ≤0.5 に届かない公算。CUDA EP なら ≈0.28 で届くが「分岐を消す」利点を捨てる。fp16 は GPU EP 全般で壊れているので「fp16 で半分」は当面無し。
- キットの改善点（次版）＝README に「N:\ 上で直接走らせない」を最上段に。`d_torch_guard` の所要は NAS の import 時間であり、constraint 修正は無害だが当該の遅さの対策にはならない。
